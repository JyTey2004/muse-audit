The native implementation

  1. The workflow preserves the exact request and freezes the interpreted checklist before generating a file.
  2. Muse produces a private draft and uploads an immutable result version.
  3. An actual read-only MCP review checks supported properties. A separately recomputed receipt must match that review.
  4. The backend requires current passing checks before canonical result retrieval. The publisher verifies the returned bytes before delivering the file.
  5. A native card displays the saved request and dated verification outcome. Its detail view reads the recorded snapshot without rechecking or changing the result.

The integration is scoped to the configured workflow. It is not a platform-wide completion veto, an operating-system sandbox or a complete observer of hidden actions. The source and private runtime context remain trusted.

The engineering behind the card

A receipt is a prerequisite for result delivery in this integrated workflow. The card presents the result; it cannot approve delivery.

Muse runs separate asynchronous work and check phases. The work phase saves the exact request and selected requirements, creates a private draft and uploads an immutable version. The check phase invokes the read-only MCP service, compares its evidence with a separately recomputed server receipt, and requests completion and the guarded result.

freeze request → draft → immutable upload → MCP review → server receipt → completion → guarded result

Implemented controls, from the reviewed submission
MechanismWhat it enforces
Native agent orchestrationSeparate bounded Muse workers create the draft and perform final checking. The saved workflow accepts the normal request only; caller-supplied bypass and delivery flags are rejected.
Read-only MCP, separate state transitionsExactly three MCP tools expose capabilities, review and recheck. Authenticated HTTP writes handle intake, upload, receipt persistence and completion. The receipt endpoint accepts a version identifier and recomputes checks; it does not accept a model-supplied verdict.
Evidence agreementRequest, task, version, artifact and checker bindings must match. The native MCP result and saved receipt are compared by a canonical SHA-256 digest over every returned field except the generation timestamp. A receipt from another task cannot authorize delivery.
Freshness at completion and downloadServer upload history selects the current version. Completion and result release recompute freshness and require every supported frozen requirement to pass. Missing, unknown, failed or changed evidence refuses release. A historical receipt alone is insufficient.
Publication integrityThe backend validates records under an owner lock and checks again immediately before atomic completion publication. The publisher downloads the guarded snapshot, compares its bytes with both artifact bindings, and creates the final file exclusively without following symlinks or overwriting different bytes.
A quiet consumer UIThe card displays selected recorded milestones and check results. Its disclosure changes widget-local state only. A fixed flex frame, scrolling details and an outside footer accommodate Muse's fixed preview height without creating follow-up messages or new agent calls.

The final attachment stays separate from the display snapshot. Card creation cannot advance task state; a preview failure cannot authorize an unchecked draft. The trusted application, source/private workflow context and evidence store remain within the trust boundary. Digest agreement does not establish source authenticity or complete natural-language requirement coverage.

Comparison with Muse alone

The 29 October exploratory comparison used six synthetic task pairs. Ordinary Muse and Muse plus Stardive each produced six correct artifacts. This does not establish an accuracy advantage. It did not measure user checking-time savings, willingness to pay, production reliability, complete semantics or privacy.

Further evaluation should compare a strong self-checking Muse baseline with the same available evidence, and measure incorrect acceptance alongside active human checking effort.

The insurance path

The retained records could become inputs to an insurer's assessment of a defined task risk. That requires real outcome and loss data, trustworthy evidence collection, agreed coverage terms and an insurer willing to accept the evidence. A passing verification record is not an insurance policy.

Munich Re's description of AI risk assessment connects underwriting to system assessment and historical performance. This is context, not a Stardive partnership or coverage commitment.

No live purchase, payment, physical delivery verification, insurance coverage or payout promise is demonstrated by this website.
